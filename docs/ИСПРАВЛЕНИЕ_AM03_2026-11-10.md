## Поведение очереди

Письма по-прежнему сначала перемещаются с флешки в локальный outbox.
Недоступность сервера сохраняет их там. Фон после ошибки возвращается к
существующему расписанию: по умолчанию следующий цикл после 300 секунд
бездействия, проверка порога каждые 30 секунд. Активность оператора сбрасывает
этот таймер. Это повтор почтовой операции, отдельный ping не добавлен.

В состоянии письма сохранены разные результаты по каждому адресу:

| Метка | Смысл | Следующая попытка |
|---|---|---|
| P | Положительный итог SMTP не получен; известный отказ либо передача ещё не начата | Автоматически повторить |
| U | Сервер мог принять письмо, но положительный итог не удалось получить/устойчиво записать | Автоматически повторить; возможен дубль |
| D | Положительный итог SMTP устойчиво записан | Повторно этому адресу не отправлять |

Таким образом, прежняя политика AM-01 «U блокирует автоповтор до решения
оператора» **заменена по явному выбору пользователя**. Исторический отчёт
AM-01 описывает прежнее проверенное поведение и сохранён. Существующие U
нового формата также повторяются без ручного сброса. Ручное подтверждение
проверенного оператором приёма остаётся доступным; исправление отвергнутого
адреса сохраняется. Подтверждение SMTP означает приём сервером, а не доказанную
доставку в конечный ящик.

При сбое канала цикл прекращает дальнейшие попытки подключения для остальных
писем: вся очередь ждёт следующего цикла. Ошибка IMAP ограничена по времени
и не мешает последующей попытке SMTP. Неудачный APPEND после успешного SMTP
показывается как ошибка сохранения копии в «Отправленные»; подтверждённые
адресаты из-за этого повторно не отправляются.

Проверки привязки аккаунта/содержимого, целостности состояния и занятости
письма сохранены. Они могут требовать исправления оператором; разрешение
дублей не означает игнорирование повреждённой записи или изменённых вложений.

## Сетевые ожидания и завершение

SMTP и IMAP используют общий неблокирующий транспорт с poll и монотонными
сроками ожидания. Короткие записи, EINTR и EAGAIN обработаны. Сокет принадлежит
перемещаемому RAII-объекту: закрывается также при раннем возврате и исключении.
QUIT/LOGOUT отправляются по возможности без ожидания ответа при закрытии.

`network_settings.conf` создаётся рядом с программой. Значения в секундах,
применяются после перезапуска; ноль, чрезмерные значения и неверный синтаксис
не заменяют безопасные значения по умолчанию:

| Параметр | По умолчанию |
|---|---:|
| DNS / подключение | 10 / 10 с |
| SMTP greeting, EHLO, AUTH, MAIL, RCPT | 300 с на ответ |
| SMTP ответ на DATA / итог после DATA | 120 / 600 с |
| Простой передачи тела или чтения IMAP literal | 180 с без прогресса |
| IMAP команда / итог APPEND | 300 / 600 с |
| TCP keepalive: начало / интервал / число проб | 30 с / 10 с / 3 |
| TCP_USER_TIMEOUT | 60 с |

Большое письмо с продолжающимся обменом не ограничено общей длительностью
в 180 секунд: срок простоя продлевается при прогрессе. Для обычных ответов
используется общий срок конкретной команды. Разные стадии SMTP соответствуют
рекомендованным интервалам [RFC 5321 §4.5.3.2](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.2).
TCP keepalive и USER_TIMEOUT помогают обнаруживать молчаливую потерю канала
раньше длинного ожидания SMTP. Точное время зависит от ядра/момента отказа;
это не обещание фиксированных 60 секунд при любой неисправности. Если ОС
не применила TCP-опции, остаются сроки команд и простоя. Параметры системных
служб/интерфейсов и общие sysctl не меняются.

Системный getaddrinfo выполняется в отдельном ограниченном worker, чтобы
вызвавший поток мог завершить ожидание по сроку/отмене. Не более четырёх
зависших resolver-worker на процесс: при заполнении новые запросы получают
ошибку, пока worker не освободится. Сам системный resolver принудительно не
останавливается; worker владеет только своими аргументами и результатом,
почтовых паролей в нём нет.

Обычный выход через меню вызывает отмену, shutdown активных сокетов и join
фонового потока. Ожидание DNS/poll реагирует на отмену короткими шагами.
Время активности теперь atomic; исключения на границе фонового потока
показывают ошибку и позволяют следующему циклу продолжиться.

## Ограничения и повторная проверка

Реальные базы, профили, переписка, ключи и значения настроек не читались.
Все данные и секреты синтетические, серверы только loopback. Реальные
почтовые сервисы, физическое отключение интерфейса/питания и все версии
ядра/сетевых устройств не проверялись. Fault injection DNS проверяет
задержку resolver, а не сбой инфраструктуры DNS. ThreadSanitizer не запускался;
полного доказательства отсутствия гонок во всём приложении нет.

Отправки после неизвестного итога могут дублироваться: это выбранная
пользователем политика надёжности. Повторяются до положительного устойчиво
записанного SMTP-итога при сохранённой работоспособной очереди. Автоматический
повтор копирования в «Отправленные» после успешного SMTP отдельно не добавлен.

При смене транспортного слоя, стадий SMTP, ядра целевой системы, отмены,
состояний очереди или расписания idle повторить соответствующие fault-тесты.
Проверенный Debug не означает попадание исправления в поставляемый пакет.

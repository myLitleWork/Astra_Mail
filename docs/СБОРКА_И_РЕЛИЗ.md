# Сборка и релиз AstraMail

Версия: `app-version.json` → сгенерированный CMake header → `--version`, меню,
manifest, папка версии и имя ZIP. Имя ELF-бинарника остаётся `AstraMail`.
Первый канонический выпуск — 3.3.0, на основе прежнего обозначения v3.3.

## Полный выпуск с Windows

```bat
tools\release.bat
```

Тот же вход без batch:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\Build-AstraMailPackage.ps1
```

Нужны Windows PowerShell 5.1, Git, OpenSSH, .NET ZIP, общий репозиторий TOOLS и
SSH alias `astra16`. Альтернативный alias задаётся `-SshHost`; TOOLS находится
через `WORKSPACE_TOOLS_ROOT` или подъём по родителям без фиксированной глубины.
Абсолютные машинные пути и SSH-учётные данные в Git не хранятся.

На builder нужны Astra Linux 1.6 x86_64, CMake 3.7+, GCC с gnu++17,
Python 3.5+, libsodium development headers, tar, readelf, sha256sum и sudo
для приватных mount/network namespace, tmpfs, loopback и отказных TCP-тестов.
Зависимости автоматически не скачиваются и не устанавливаются.

Сценарий синхронно выполняет:

1. Preflight доступности инструментов, SSH, изоляции и настроенного CloudRoot.
2. Общую блокировку проекта от одновременного Release.
3. Fingerprint разрешённых исходных файлов; при изменении с прошлого выпуска
   повышается patch. Первый запуск сохраняет 3.3.0; одинаковые входы номер
   не расходуют. Сам файл версии и отчёты аудитов в fingerprint не входят.
4. Передачу allowlist в новый приватный `/tmp/astramail-release.*` на builder,
   сверку архива и каждого входа. HOME сборки и тестов изолированы.
5. Полную новую Release-сборку и все восемь native/TCP/PTY-наборов — 474
   проверки текущего baseline. Debug-сборки не подменяют этот результат.
6. Проверку встроенной версии и 64-битного ELF, реального CSV-импортёра и
   импорта образца через UI копии готового пакета на синтетическом профиле.
7. Формирование чистого пакета с manifest/checksums, обратное копирование и
   независимую сверку файлов на Windows.
8. Общую публикацию через `Publish-ReleasePackageIfConfigured.ps1` с
   `-UseForwardSlashEntryNames`: вложенные имена ZIP используют `/`, в том
   числе под Windows PowerShell 5.1.
9. Проверку возвращённых ZIP/SHA256, передачу именно опубликованного ZIP
   обратно на builder, распаковку, проверку всех SHA-256, запуска `--version`
   и CSV-импорта. Успех возвращается только после этого.

Локальные артефакты, протоколы и `release-result.json` сохраняются под
`out/release-runs/<идентификатор>/`. Каноническая локальная папка пакета
возвращается в `PackageDirectory`; не вычисляйте её по предположению.
Предыдущие запуски не удаляются и рабочая установка не обновляется.
Сценарий не делает commit/push; manifest отражает фактический HEAD и dirty.

## Публикация

Общий порядок выбора корня: `-CloudRoot` → process env
`WORKSPACE_RELEASE_CLOUD_ROOT` → одноимённая User env. В настроенном корне:

```text
AstraMail/<версия>/AstraMail-<версия>.zip
AstraMail/<версия>/AstraMail-<версия>.zip.sha256
```

Полная папка пакета в облако не копируется. Общий helper публикует пару
с восстановлением прежней пары при ошибке замены. Если корень не задан,
выдаётся явный `Cloud publish skipped`, остаётся локальный пакет. Для
намеренного локального выпуска — `tools\release.bat -SkipCloudPublish`.
Доставка Google Drive на другие устройства проверяется отдельно от создания
локально смонтированных ZIP/SHA256.

Ошибка любого обязательного этапа означает ненулевой exit code. Дождитесь
завершения исходного запуска и разберите его вывод. После уже выполненного
version sync повтор той же попытки: `tools\release.bat -SkipVersionBump`.
Повтор полного workflow создаёт отдельный run; новый bump не делается.

## Состав пакета

- `AstraMail`, `Run-AstraMail.sh`, `Verify-Package.sh`, `version.txt`,
  `app-version.json`, manifest и SHA-256 файлов.
- `lib/libsodium.so.18`, уведомления libsodium/GCC runtime; glibc и системные
  библиотеки берутся из Astra Linux. Сборка сохраняет прежние static-libstdc++
  и filesystem-флаги.
- `contacts-import-example.csv` рядом с бинарником: UTF-8 без BOM, запятая,
  LF, три вымышленных контакта `example.invalid`.
- Краткий README и русские инструкции запуска/обновления и импорта.

Рабочие `.astramail`, профиль, настройки, почта, базы и секреты не сканируются
и не копируются. Fingerprint обходит только `src`, `secrets` (исходный код
backend, не пользовательское хранилище), `cmake`, `scripts`, `tools`,
`deployment`, `tutorials`, `tests` с allowlist расширений и четыре явных
корневых файла: CMakeLists.txt, main.cpp, README.md, .gitignore. Reparse points
отклоняются. Generated/build/out/runtime-каталоги не посещаются.

## Обычная сборка на Linux

```sh
mkdir build-debug
cd build-debug
cmake .. -DCMAKE_BUILD_TYPE=Debug
cmake --build . -- -j2
```

Обычный CMake сохраняет прежний экспорт бинарника в `~/export/AstraMail` и
install target `/usr/local/bin`; эти операции не являются публикацией
версионного пакета. В canonical workflow экспорт идёт в отдельный HOME
сборки. Install target при выпуске не вызывается.

Проверки сценариев без выпуска: `powershell.exe -NoProfile -ExecutionPolicy
Bypass -File scripts/tests/Test-AstraMailRelease.ps1`.
